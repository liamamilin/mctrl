# M4. Language Action State Model｜语言行动状态模型

版本 v0.7 · 完整体系发布稿。

观察语言与既有规则下的请求、责任、承诺、权限、任务、协调和治理关系。语言行动的有效性取决于角色、来源、接收和制度条件。

理解、接受、承诺、提交、验收及实际结果分开；明确接受不是所有制度义务唯一来源。AI 可以处于技术任务关系，但不据其措辞认定具有人类义务体验。

本模型登记 29 个接口：16 个 P 编号、13 个 Composite。P 表示当前工程粒度，不是心理机制不可再分的证明。

**接口组织：** 本模型以请求（Request）、规格（Specification）、任务（Task）、角色（Role）、承诺（Commitment）、协作（Coordination）组织接口。请求向他方提出行动要求，规格将相关工作定义为有目的、范围、交付和验收条件的任务对象；任务集中说明执行方是否接受，以及结果是否按标准完成。

角色明确任务中的责任和权限，承诺在适用规则下建立对特定行为或结果的义务；任务接受与承诺相关，但分别判断其成立。

协作将多个任务、角色和承诺连接起来，通过依赖、交接、规则与治理组织共同工作，并根据实际反馈稳定或修订这些关系。

以下构造情境说明这些组怎样连接：甲请求乙整理文档；双方明确整理哪一版、交付什么、怎样检查，这是规格。乙接受按该版本执行整理工作，属于任务接受；后来交付是否满足规则是任务完成的另一个判断。假设双方已有安排，由甲确认验收；甲有验收角色的依据来自这项安排，不能由本书替现实参与者授予。若乙另按双方适用约定作出交付承诺，再检查承诺关系。乙的交付还需丙提供材料时，协作说明丙交什么、乙何时可开始、阻塞怎样处理。每种新增关系都要有其材料或成立条件，不能从上一组名称直接推出。

## 使用约定

任务完成、承诺履行与协调稳定还依赖真实执行和结果。有关模式组织核验、反馈或修订，支持按材料判断这些状态；不能靠说出验收句、履行句或稳定句完成现实工作。

语言模式用于把算子落实为语言操作，指向本接口的变化。每项先给一条可直接背诵的核心句，再给展开：核心句提示操作方向；展开是可直接填入内容、用于自问或交流的表达，写清对什么做什么。完成检查另说明怎样判断结果。〔……〕是待填位置；对象也可由前文提供。按缺口选用必要展开，已有状态可复用；一个模式不必独自完成复合接口，也不要求同时使用全部链接。是否发生变化仍看完成检查，不能凭说出核心句判定。

操作入口列出可选方法；按当前缺口和方法前提选择，不要求逐项调用。需要组织完整任务时再参考协议；仍然有效的已有状态直接复用。

答不上展开时，先回到材料、原话或具体情境做起手操作；不知道的名称、规则或路径可以在处理后逐步形成。展开中的候选、草稿等位置可以在下一轮填入，不要求一开始已有答案。缺少事实材料、领域方法或有效授权时先取得相应输入，不能靠换问法制造答案。

条目机制映射均为工程解释候选；针对此目标的 CLE 干预效果默认 E0，即尚无该效果主张的验证；工程定义被采用与效果验证是两件事。Composite 的“组成”列表示可复用过程，不规定全部必经；已有输入直接复用。失败、无变化与信息不足都须保留。

卡片箭头写接口的变化方向；本次是否具备前状态、是否发生变化，须另用材料判断。没有前状态时先检查当前情况，不倒推此前“没有”或“不会”。详见[状态与变化](../STATE_SPEC.md)。

## 请求（Request） {#request}

请求向可识别的对象提出可响应的行动要求；意图是主体准备做什么的内部方向。把意图写成消息，只证明尝试表达；请求是否到达、理解和成立另查，接受是对方的响应事件。

<a id="a-p1"></a>

### 请求形成（Request Formation） · A-P1

**状态变化：** 无有效请求 → 已建立可响应请求。

在适用沟通规则下，向识别的对象提出可理解的行动要求。

**相邻区别：** 请求形成建立可响应的行动要求；[请求处理](../models/M4.md#a-c1)组织该请求的接受、拒绝、协商等响应。

**操作入口：** [OP26](../engineering/OPERATORS.md#op26)。

**怎样做：** 明确接收者、行为和响应方式；提出请求；检查到达与成立依据。

**语言模式：** [LP26](../engineering/PATTERNS.md#lp26)。

**核心句：** “请你做这件事，并告诉我能否接受。”

**展开：** “〔接收者〕，请你在〔必要条件或期限〕下完成〔具体行为〕。请通过〔响应方式〕告诉我：接受、拒绝，还是需要调整哪些条件？”

**完成检查：** 请求对象、行为、响应方式明确，并有足够接收依据。

按当前沟通情境核对到达、必要理解与成立依据；前文已有的条件可复用。发送、请求成立、接受和完成分别判断，误解时先澄清。

**边界与失效：** 未到达只是尝试发送；请求不意味着接受，存在义务与否看既有规则。

**机制候选：** [ME11](../MECHANISMS.md#me11)、[ME12](../MECHANISMS.md#me12)。

<a id="a-c1"></a>

### 请求处理（Request Resolution） · A-C1

**状态变化：** 有效请求 → 接受／拒绝／协商／延后／撤回。

理解请求并按能力、条件或规则形成响应，必要时回到协商。

**操作入口：** [OP26](../engineering/OPERATORS.md#op26)、[OP24](../engineering/OPERATORS.md#op24)、[OP20](../engineering/OPERATORS.md#op20)。完整任务可参照[PR09](../engineering/PROTOCOLS.md#pr09)。

**怎样做：** 确认有效请求与理解；由响应方形成接受、拒绝或协商状态；记录待处理条件。

**语言模式：** [LP26](../engineering/PATTERNS.md#lp26)、[LP24](../engineering/PATTERNS.md#lp24)、[LP20](../engineering/PATTERNS.md#lp20)。

**核心句：** “我对这个请求的响应是接受、拒绝或协商。”

**展开：** “对于〔请求〕，我理解你希望我〔具体行为〕。我的响应是〔接受、拒绝、协商或延后〕，条件或待确认部分是〔内容〕，下一次由〔主体〕在〔条件〕下响应。”

**完成检查：** 响应状态、待处理条件和下一响应责任明确。

撤回由提出者或适用规则处理；未知、未响应和协商中分别记录，不代对方填写接受。

**边界与失效：** 分支本身不证明复合性；协商与延后仍可能未关闭。

**可复用组成：** [A-P1](../models/M4.md#a-p1)、[I-C3](../models/M3.md#i-c3)、[C-C10](../models/M2.md#c-c10)、[A-P10](../models/M4.md#a-p10)、[A-P4](../models/M4.md#a-p4)。

**机制候选：** [ME10](../MECHANISMS.md#me10)、[ME12](../MECHANISMS.md#me12)。

## 规格（Specification） {#specification}

这里的任务是主体或系统之间可共同指涉的行动要求对象；规格说明它的目的、范围、交付、约束与验收等条件。“绑定”指把字段纳入指定任务版本和有效安排，不能仅凭写上文字判定生效。交付说明给什么，验收标准说明怎样判定满足。M2的具体化同样使用Specification英文，但处理的是认知对象，不等于形成社会任务规格。

<a id="a-p9"></a>

### 任务定义（Task Definition） · A-P9

**状态变化：** 任务对象不明 → 可辨认任务对象。

把任务内容建立为主体间可指涉、可版本化的对象。

**相邻区别：** 任务定义建立可共同指涉的任务对象；[可执行规格形成](../models/M4.md#a-c6)进一步补足指导执行和验收所需的规格。

**操作入口：** [OP28](../engineering/OPERATORS.md#op28)。

**怎样做：** 从原始需求或请求开始，先描述想做的活动或希望取得的变化；给这份描述一个暂称和版本，请相关方核对是否指向同一项任务。正式名称未知不阻断记录，目的、执行者等未明字段保留缺项。

**语言模式：** [LP28](../engineering/PATTERNS.md#lp28)。

**核心句：** “先描述要做的事，再建立任务称呼和版本。”

**展开：** “〔原始需求或请求〕里，希望做什么或取得什么变化？请先用日常话描述，暂称为〔任务称呼〕，记录版本。相关方是否指向同一项任务，它服务什么对象或目标，目的、执行者和期限等还缺什么？”

**完成检查：** 能识别任务及目标对象，尚缺规格字段明确。

核对相关方能否指向同一任务对象及版本；建立任务记录不自动表示已指派或接受。

**边界与失效：** 任务存在不意味着已指派、接受或可执行。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p12"></a>

### 任务目的定义（Goal Definition） · A-P12

**状态变化：** 规格目的未绑定 → 任务目的已绑定。

将目标写入任务规格，指出交付服务于哪个结果。

**相邻区别：** 任务目的定义将目的绑定到任务规格；[目标采纳](../models/M2.md#c-p18)是主体内部采纳追求对象，两者分别确认。

**操作入口：** [OP28](../engineering/OPERATORS.md#op28)。

**怎样做：** 将目的绑定到任务版本；核对有权确定者的确认；区分个人目标。

**语言模式：** [LP28](../engineering/PATTERNS.md#lp28)。

**核心句：** “把这项任务服务的目的绑定到规格。”

**展开：** “对于〔任务及版本〕，提议将目的确定为〔希望服务的结果〕。请有权确定者根据〔适用安排〕确认采用，或指出需要修改的地方。”

**完成检查：** 目的可识别且由有权确定者确认。

有有效确认才记录目的已绑定；缺少来源或确认时保留提案，不与个人目标采纳混同。

**边界与失效：** 是 M4 规格字段事件，不等于主体内部 C-P18。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p13"></a>

### 范围定义（Scope Definition） · A-P13

**状态变化：** 任务范围未定 → 范围已绑定。

将包含项、排除项和适用环境纳入任务。

**操作入口：** [OP28](../engineering/OPERATORS.md#op28)、[OP10](../engineering/OPERATORS.md#op10)。

**怎样做：** 从任务目的和具体活动出发，列出会被一起考虑的事项；用做与不做这些事项会影响什么的例子，提出纳入与排除范围，再由适用角色确认版本和变更方式。不会判断的项保留待确认。

**语言模式：** [LP28](../engineering/PATTERNS.md#lp28)、[LP10](../engineering/PATTERNS.md#lp10)。

**核心句：** “先用具体事项试范围，再确认纳入与排除。”

**展开：** “为了〔任务目的〕，哪些具体事项可能涉及〔任务及版本〕？做或不做〔事项〕会影响什么？据此提议本次纳入哪些、排除哪些、哪些待确认，再请〔适用角色〕按安排确认范围及以后的变更方式。”

**完成检查：** 可判断范围内外例子并记录版本。

**边界与失效：** 思考边界属于 C-P13；成为任务约定才是此处输出。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p14"></a>

### 交付定义（Deliverable Definition） · A-P14

**状态变化：** 交付物不明 → 交付对象已绑定。

约定交付物、格式、位置或可观察结果。

此处先定义要交什么，不要求产物已经存在。定义阶段检查接收方能否按约定辨认预期产物及找到交付位置，例如指出将要提交的对照表与目录；交付后再检查实际文件是否在该位置。不能把“位置已约定”写成“文件已提交”。

**相邻区别：** 交付定义说明要交付什么、以何种形式放在哪里；[验收标准形成](../models/M4.md#a-p16)说明凭什么材料及规则判定交付满足要求。

**操作入口：** [OP28](../engineering/OPERATORS.md#op28)。

**怎样做：** 先询问接收方取得结果后要查看、使用或核验什么，再据此提出可辨认的产物或可观察结果、形式和位置；必要时参考样例，由适用角色确认并绑定任务版本。需求仍不明时先澄清，不先挑文件格式代替内容。

**语言模式：** [LP28](../engineering/PATTERNS.md#lp28)。

**核心句：** “先问结果怎样被使用，再约定交付形式。”

**展开：** “取得〔任务〕的结果后，接收方要查看、使用或核验什么？据此提议交付〔内容或可观察结果〕，采用〔合适形式〕，放在〔位置或渠道〕。需要参考什么样例？请按适用安排确认如何辨认任务版本和找到预期产物。”

**完成检查：** 接收方能够找到并识别交付物。

交付定义清楚不证明质量合格；质量按验收规则另查。

**边界与失效：** 产物存在不等于质量达标或目标达到。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p15"></a>

### 约束显化（Constraint Explication） · A-P15

**状态变化：** 任务约束隐含／未绑定 → 约束纳入规格。

明确资源、依赖、允许行为与禁止项。

**操作入口：** [OP28](../engineering/OPERATORS.md#op28)。

**怎样做：** 明确资源、依赖、允许与禁止项；纳入有效规格；检查升级条件。

**语言模式：** [LP28](../engineering/PATTERNS.md#lp28)。

**核心句：** “把允许、禁止和依赖条件纳入任务规格。”

**展开：** “对于〔任务及版本〕，有哪些资源、前置依赖、允许或禁止事项，依据是什么？请由〔适用角色〕确认纳入规格，并用具体情况说明哪些可执行、哪些禁止、哪些需升级确认。”

**完成检查：** 执行者可区分允许、禁止与需要升级确认的情况。

**边界与失效：** 发现约束是认知工作；此接口记录其社会规格地位。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p16"></a>

### 验收标准形成（Acceptance-Criteria Formation） · A-P16

**状态变化：** 完成判断未约定 → 验收标准纳入规格。

绑定标准、检验材料、方式与所需验收权。

**操作入口：** [OP28](../engineering/OPERATORS.md#op28)、[OP18](../engineering/OPERATORS.md#op18)。

**怎样做：** 已有可适用规则时直接复用；规则尚缺时，先比较任务中可接受与不可接受的具体结果，结合目的和约束形成规则候选，再试判其他实例。将规则、材料、核验方式与有权验收角色确认绑定到任务版本。

**语言模式：** [LP28](../engineering/PATTERNS.md#lp28)、[LP18](../engineering/PATTERNS.md#lp18)。

**核心句：** “先试判具体结果，再确认验收约定。”

**展开：** “对于〔任务及版本〕，已有可用规则吗？没有时，哪些具体结果可以接受、哪些不能接受，区别为何影响任务目的？据此提出〔规则候选〕，用其他实例试判满足、失败和缺材料，再确认使用哪些材料、怎样核验及由谁按安排验收。”

**完成检查：** 满足、失败、无法验证三种情况可区分。

**边界与失效：** 标准设计可以是复杂认知过程；P 编号表示绑定事件而非原子心理过程。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-c6"></a>

### 可执行规格形成（Executable Specification Formation） · A-C6

**状态变化：** 模糊任务 → 足以执行与验收的任务规格。

明确目的、范围、交付、约束、验收，以及执行方、资源、依赖和异常处理。

这里先检查规格能否指导下一步：做什么、需要什么、怎样验收、缺条件时找谁。执行者能说清这些，不表示账号、资料和资源此刻已可用；实际能否开始，按本页末尾的“任务就绪”检查另取材料。

**操作入口：** [OP28](../engineering/OPERATORS.md#op28)、[OP26](../engineering/OPERATORS.md#op26)、[OP29](../engineering/OPERATORS.md#op29)。完整任务可参照[PR09](../engineering/PROTOCOLS.md#pr09)。

**怎样做：** 从现有任务描述试走执行方下一步：先做什么、用什么输入、得到什么交付、怎样验收、缺条件找谁；在答不上来的地方只补必要规格，按安排取得确认。接受、实际资源可用与真正开始分别核验。

**语言模式：** [LP28](../engineering/PATTERNS.md#lp28)、[LP26](../engineering/PATTERNS.md#lp26)、[LP29](../engineering/PATTERNS.md#lp29)。

**核心句：** “先试走下一步，再补阻止执行或验收的缺项。”

**展开：** “面对〔现有任务描述〕，执行方第一步要做什么、需要什么输入、产生什么交付，接收方怎样验收？缺输入或发生阻塞时找谁？请在答不上来的地方补必要目的、范围、约束、角色或依赖，再按安排确认；哪些实际开始条件还需核验？”

**完成检查：** 执行方能开始下一步、识别完成与阻塞，并有升级路径。

用一个正常和一个关键阻塞情境检查规格；接受、资源实际可用和实际开始分别取得依据。

**边界与失效：** 足够执行不等于可行性已证实；无需把所有技术细节预先指定。

**可复用组成：** [A-P9](../models/M4.md#a-p9)、[A-P12](../models/M4.md#a-p12)、[A-P13](../models/M4.md#a-p13)、[A-P14](../models/M4.md#a-p14)、[A-P15](../models/M4.md#a-p15)、[A-P16](../models/M4.md#a-p16)、[A-P10](../models/M4.md#a-p10)、[A-C8](../models/M4.md#a-c8)。

**机制候选：** [ME10](../MECHANISMS.md#me10)、[ME12](../MECHANISMS.md#me12)。

## 任务（Task） {#task}

工程任务是本次要解决什么问题；本组的社会任务是按有关工作安排定义的行动要求对象。接受说明执行方接受哪个版本与条件；完成说明结果满足任务条件及所需关闭依据。关闭是按适用安排结束处理状态，停止聊天或提交文件不会自动关闭任务。

<a id="a-p10"></a>

### 任务接受（Task Acceptance） · A-P10

**状态变化：** 已定义／指派任务 → 执行方明确接受。

执行方接受指定版本、条件与资源范围的任务。

**相邻区别：** 任务接受记录执行方接受指定版本与条件；[承诺形成](../models/M4.md#a-p4)另按适用规则检查承诺义务是否成立。

**操作入口：** [OP26](../engineering/OPERATORS.md#op26)、[OP28](../engineering/OPERATORS.md#op28)。

**怎样做：** 由执行方明确响应；绑定被接受版本、条件与期限；拒绝或未知另记。

**语言模式：** [LP26](../engineering/PATTERNS.md#lp26)、[LP28](../engineering/PATTERNS.md#lp28)。

**核心句：** “我接受这个版本的任务及其条件。”

**展开：** “我接受〔任务及版本〕，在〔条件〕下执行，约定期限为〔期限〕；接受范围是〔范围〕，仍待确认的部分是〔内容〕。”

**完成检查：** 记录执行方、任务版本、接受条件和期限。

记录执行方实际响应；拒绝、反提案、无响应与接受分开，不由他人代为接受。

**边界与失效：** 有效制度指派可先产生角色义务；明确接受仍是另一可记录事件。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p11"></a>

### 任务完成（Task Completion） · A-P11

**状态变化：** 任务待完成／已提交 → 按标准判定完成。

将交付结果与预定完成条件匹配，并由所需角色关闭。

**相邻区别：** 任务完成按任务的完成条件核验结果；[承诺履行](../models/M4.md#a-p5)按有效承诺的条件判断履行，关闭一项任务不自动结束全部承诺。

**操作入口：** [OP37](../engineering/OPERATORS.md#op37)。完整任务可参照[PR12](../engineering/PROTOCOLS.md#pr12)。

**怎样做：** 取得真实交付；按已约定标准和角色核验；记录通过、未通过或无法核验。

**语言模式：** [LP39](../engineering/PATTERNS.md#lp39)。

**核心句：** “拿真实交付逐项验收，再确认完成。”

**展开：** “请将〔真实交付及版本材料〕逐项对照〔已约定标准〕，记录通过、未通过或无法核验及依据。满足〔适用关闭条件〕后，请〔有权角色或约定系统〕确认完成或关闭并保留记录。”

**完成检查：** 交付证据、标准版本和关闭依据可追溯。

实际交付、标准版本和关闭依据分别核对；自报完成或一句确认不能代替这些材料。

**边界与失效：** 提交与验收分开；无需一概要求人工，但必须有约定验证方式。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

## 角色（Role） {#role}

角色是安排中的执行、负责、决定或验收位置；责任是对结果或事项负责的关系；权限是按规则有效的决定、批准或控制权。“认可”指取得适用规则所需的确认，仍须检查来源。技术访问则说明系统此刻是否允许某项操作，不能与社会职权互相推出。

下文回滚指撤回本次变更，尝试回到此前版本或状态；能否恢复还需真实材料，批准回滚的权限与执行它的技术能力也分别检查。

“按适用规则”不是空白授权：应找出本任务已有约定、有效指派或其他可查来源，说明它允许谁在什么范围作什么确认。如果来源未取得，先记主张或提案。文档例句中出现“负责人”只展示一种可能安排，不证明现实中该人已经有权；CLE也不替代有关领域对来源有效性的判断。

<a id="a-p2"></a>

### 责任主张（Responsibility Claim） · A-P2

**状态变化：** 责任主张未明确 → 主体主张责任。

主体声明对某范围负责。

**相邻区别：** 责任主张记录主体提出了什么负责范围；[责任认可](../models/M4.md#a-p3)检查安排是否取得适用规则所需的认可。

**操作入口：** [OP29](../engineering/OPERATORS.md#op29)。

**怎样做：** 由主张者声明负责对象与范围；记录时间；把主张与所需认可分开。

**语言模式：** [LP29](../engineering/PATTERNS.md#lp29)。

**核心句：** “我主张对这件事负责。”

**展开：** “我在〔时间〕主张对〔事项与范围〕负责，不包含〔排除事项〕，所称依据是〔来源〕。”

**完成检查：** 记录主张者、范围与提出时间。

先记录谁提出什么范围的主张；有效认可及所需权限另核验。

**边界与失效：** 主张可以与既有责任冲突；不自动代表团队认可或能力充分。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p3"></a>

### 责任认可（Responsibility Acceptance） · A-P3

**状态变化：** 责任安排未获所需认可 → 安排按规则被认可。

确定责任关系获得相关主体或授权安排所需的认可。

**操作入口：** [OP29](../engineering/OPERATORS.md#op29)。

**怎样做：** 定位责任安排及来源；核对所需认可；记录范围与权限缺口。

**语言模式：** [LP29](../engineering/PATTERNS.md#lp29)。

**核心句：** “按有效依据确认谁对什么负责。”

**展开：** “根据〔有效来源〕，提议由〔负责者〕对〔事项及范围〕负责。请按〔适用规则〕取得所需认可，并明确尚缺权限和升级渠道。”

**完成检查：** 记录认可依据、负责者、范围、权限缺口。

核对来源和实际认可材料；来源或认可不足时保留待定。

**边界与失效：** 包括从有效指派进入认可，不要求一定先自我主张；责任不等于决策权。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-c2"></a>

### 共同责任形成（Shared Responsibility Formation） · A-C2

**状态变化：** 责任未协调 → 分布或共同责任结构。

确定负责结果、贡献范围、接口、边界和升级方式。

**操作入口：** [OP29](../engineering/OPERATORS.md#op29)、[OP28](../engineering/OPERATORS.md#op28)。完整任务可参照[PR11](../engineering/PROTOCOLS.md#pr11)。

**怎样做：** 从关键结果及所需贡献出发，先问各主体能承担什么、哪些结果仍无人负责；据此提出分别与共同负责范围、交接及冲突处理，由适用主体按规则认可。能力信息未知时不代填承担。

**语言模式：** [LP29](../engineering/PATTERNS.md#lp29)、[LP28](../engineering/PATTERNS.md#lp28)。

**核心句：** “先查结果需要谁的贡献，再协调责任范围。”

**展开：** “〔关键结果〕需要哪些贡献，各主体能承担什么，哪些仍未知或无人负责？据此提议分别与共同负责的范围，交接缺口或冲突由谁处理？请相关主体按〔适用规则〕确认这份责任安排。”

**完成检查：** 每个关键结果有负责范围与冲突处理方法。

**边界与失效：** 共同责任不是谁都可以不负责；不要求先有单一责任。

**可复用组成：** [A-P2](../models/M4.md#a-p2)、[A-P3](../models/M4.md#a-p3)、[A-P13](../models/M4.md#a-p13)、[A-C8](../models/M4.md#a-c8)。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p7"></a>

### 权限主张（Authority Claim） · A-P7

**状态变化：** 权限主张未明确 → 权限被主张。

主体声明具有某范围的批准、决策或控制权。

**相邻区别：** 权限主张记录主体声称具有什么权；[权限认可](../models/M4.md#a-p8)检查该权限关系的来源、边界与所需认可。

**操作入口：** [OP29](../engineering/OPERATORS.md#op29)。

**怎样做：** 声明主张的决定或控制范围；记录来源声明；另查有效性和认可。

**语言模式：** [LP29](../engineering/PATTERNS.md#lp29)。

**核心句：** “我主张有权决定这件事。”

**展开：** “我主张对〔对象及范围〕有权作〔决定或控制行为〕，所称依据为〔来源〕，提出时间为〔时间〕。”

**完成检查：** 记录主张及适用对象，而非直接升级为有效授权。

主张可先记录；有效来源、所需认可和技术访问另核验，不凭声明登记有效授权。

**边界与失效：** 主张不保证制度有效、他人认可或技术访问可用。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p8"></a>

### 权限认可（Authority Recognition） · A-P8

**状态变化：** 权限关系待定 → 按规则被认可。

检查授权来源、相关主体认可及作用范围。

**操作入口：** [OP29](../engineering/OPERATORS.md#op29)。

**怎样做：** 核对授权来源、范围和期限；取得所需认可；技术访问另核验。

**语言模式：** [LP29](../engineering/PATTERNS.md#lp29)。

**核心句：** “核对授权来源，按规则确认权限。”

**展开：** “对于〔权限〕，授权来自哪里，适用范围、期限和撤销条件是什么？请按〔适用规则〕核对并取得所需认可，注明依据。”

**完成检查：** 可追溯依据、边界、期限与撤销条件。

相关技术访问另用系统材料核验；缺少来源或认可时权限保持待定。

**边界与失效：** 认可不代替来源有效性；技术权限另需系统证据。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-c4"></a>

### 权限定义（Authority Definition） · A-C4

**状态变化：** 权限结构不清 → 有范围与来源的权限结构。

明确决定、批准、撤销、覆盖、升级及必要技术访问条件。

**相邻区别：** 权限定义明确谁在什么范围有何权；[权限转移](../models/M4.md#a-c5)检查既有权限怎样按规则转移及何时生效。

**操作入口：** [OP29](../engineering/OPERATORS.md#op29)、[OP31](../engineering/OPERATORS.md#op31)。完整任务可参照[PR11](../engineering/PROTOCOLS.md#pr11)。

**怎样做：** 列关键决定；核对有权角色、来源与边界；处理覆盖、撤销及升级。

**语言模式：** [LP29](../engineering/PATTERNS.md#lp29)、[LP31](../engineering/PATTERNS.md#lp31)。

**核心句：** “明确谁能决定什么，以及权限边界。”

**展开：** “对于〔关键决定〕，根据〔有效来源〕，谁能决定什么，范围和期限是什么？覆盖、撤销、例外和升级由谁怎样处理？请按适用安排确认这份权限结构。”

**完成检查：** 每类关键决定能找到有权角色和依据。

**边界与失效：** 职位、责任和技术凭证不能自动互相推出。

**可复用组成：** [A-P7](../models/M4.md#a-p7)、[A-P8](../models/M4.md#a-p8)、[A-P13](../models/M4.md#a-p13)、[A-C11](../models/M4.md#a-c11)。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-c5"></a>

### 权限转移（Authority Transfer） · A-C5

**状态变化：** 原有效权限结构 → 按规则转移的权限结构。

核验转移者权限、范围、生效、接收认可和原权限处理。

**操作入口：** [OP29](../engineering/OPERATORS.md#op29)、[OP30](../engineering/OPERATORS.md#op30)。完整任务可参照[PR11](../engineering/PROTOCOLS.md#pr11)。

**怎样做：** 核验转移资格与可转移范围；办理所需认可；记录旧权、期限与技术配置。

**语言模式：** [LP29](../engineering/PATTERNS.md#lp29)、[LP30](../engineering/PATTERNS.md#lp30)。

**核心句：** “按转移规则调整权限，并记录生效状态。”

**展开：** “提议将〔权限及范围〕从〔原主体〕转给〔新主体〕。依据〔转移规则〕，是否具备资格和可转范围？请办理所需认可，说明生效点、期限、旧权保留及技术配置安排。”

**完成检查：** 旧权限是否保留、转移期限和技术配置状态明确。

提议与生效分别记录；未生效部分保留原状态，授权委托、转移和复制访问分别判断。

**边界与失效：** 可转移、授权委托、复制访问是不同关系；不能强制旧权必然完全释放。

**可复用组成：** [A-P7](../models/M4.md#a-p7)、[A-P8](../models/M4.md#a-p8)、[A-P13](../models/M4.md#a-p13)、[A-C4](../models/M4.md#a-c4)。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-c7"></a>

### 角色组织（Role Structuring） · A-C7

**状态变化：** 角色未协调 → 角色及接口结构。

绑定角色职责、决策权、交接、替补和适用范围。

**相邻区别：** 角色组织关联执行、负责、决定与验收位置；[共同责任形成](../models/M4.md#a-c2)集中明确关键结果由哪些主体承担哪些责任。

**操作入口：** [OP29](../engineering/OPERATORS.md#op29)、[OP28](../engineering/OPERATORS.md#op28)。完整任务可参照[PR11](../engineering/PROTOCOLS.md#pr11)。

**怎样做：** 绑定执行、负责、决定与验收角色；核对来源、交接及替补；取得认可。

**语言模式：** [LP29](../engineering/PATTERNS.md#lp29)、[LP28](../engineering/PATTERNS.md#lp28)。

**核心句：** “把执行、负责、决定和验收角色接起来。”

**展开：** “对于〔任务〕，谁执行、谁负责、谁决定、谁验收，各自依据和范围是什么？交接、冲突及缺席时由谁接替？请按适用安排确认各角色关系。”

**完成检查：** 谁执行、谁负责、谁验收可以不同且被明确。

**边界与失效：** 身份标签不自动赋予职权，需相关关系成立。

**可复用组成：** [A-P3](../models/M4.md#a-p3)、[A-P8](../models/M4.md#a-p8)、[A-P13](../models/M4.md#a-p13)、[A-C2](../models/M4.md#a-c2)、[A-C4](../models/M4.md#a-c4)。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

## 承诺（Commitment） {#commitment}

承诺是在适用规则下对相对方建立的特定义务关系；义务是应当实施或避免某行为的要求，也可来自既有有效职责。履行满足承诺条件；解除按有效依据结束指定尚未履行义务；重新协商提出或形成新的约定。内部决心与这类主体间关系分别记录。

<a id="a-p4"></a>

### 承诺形成（Commitment Formation） · A-P4

**状态变化：** 未建立承诺 → 按适用规则建立承诺。

明确谁对谁承诺什么、条件与时间；采用既有角色和规则判断成立。

**操作入口：** [OP27](../engineering/OPERATORS.md#op27)。

**怎样做：** 明确承诺者、相对方、内容及条件；检查成立规则；记录例外。

**语言模式：** [LP27](../engineering/PATTERNS.md#lp27)。

**核心句：** “我承诺按这些条件完成这件事。”

**展开：** “我向〔相对方〕承诺在〔条件与期限〕下完成〔事项〕；例外按〔程序〕处理，修改或解除依据为〔约定或规则〕。”

**完成检查：** 可以辨认义务内容、受益方、例外和确认依据。

**边界与失效：** 不要求每种承诺都有明示双向接受；不能凭一句“我会做”自动判定。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p5"></a>

### 承诺履行（Commitment Fulfillment） · A-P5

**状态变化：** 未履行承诺 → 满足承诺条件。

将实际结果按既有承诺条件核验并记录履行。

**操作入口：** [OP37](../engineering/OPERATORS.md#op37)。完整任务可参照[PR12](../engineering/PROTOCOLS.md#pr12)。

**怎样做：** 取得实际结果；按有效承诺条件核验；满足所需关闭依据后记录履行。

**语言模式：** [LP39](../engineering/PATTERNS.md#lp39)。

**核心句：** “用真实结果核验承诺是否履行。”

**展开：** “请将〔真实结果及材料〕逐项对照〔有效承诺及版本〕的条件，记录满足、未满足或无法核验及依据。满足〔所需关闭条件〕后，按规则记录履行状态。”

**完成检查：** 具备结果证据、条件匹配和所需关闭依据。

核验依赖真实结果；实际做了动作或自报完成不直接证明满足承诺条件。

**边界与失效：** 仅执行动作或自报完成不足；核验依赖 O-C2。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-p6"></a>

### 承诺解除（Commitment Release） · A-P6

**状态变化：** 有效承诺 → 按规则解除义务。

在有权解除者或既有条件的依据下解除尚未履行的承诺。

**相邻区别：** 承诺解除按有效依据结束指定义务；[承诺重新协商](../models/M4.md#a-c3)协商修订承诺，提议未生效前旧义务依原规则处理。

**操作入口：** [OP30](../engineering/OPERATORS.md#op30)。

**怎样做：** 定位有效承诺和有权解除者或解除条件；核对依据；记录剩余义务和生效。

**语言模式：** [LP30](../engineering/PATTERNS.md#lp30)。

**核心句：** “依照有效依据解除指定范围的承诺。”

**展开：** “对于〔有效承诺〕，依据〔有权解除者或已满足的解除条件〕，提议解除〔指定义务范围〕。请核对依据并办理所需程序，说明生效点、受影响者和剩余义务。”

**完成检查：** 解除依据、范围和影响者明确，历史保留。

只有满足解除规则才登记解除；失约、遗忘或单方退出不自动结束义务，历史记录保留。

**边界与失效：** 失约、忘记或单方退出不等于有效解除。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-c3"></a>

### 承诺重新协商（Commitment Renegotiation） · A-C3

**状态变化：** 既有承诺需调整 → 认可后的修订承诺。

解释变化、提出修订、确认影响方及旧承诺何时被替代。

**操作入口：** [OP30](../engineering/OPERATORS.md#op30)、[OP27](../engineering/OPERATORS.md#op27)。完整任务可参照[PR09](../engineering/PROTOCOLS.md#pr09)。

**怎样做：** 定位旧承诺及变化；提出修订；取得认可并记录新旧义务与生效点。

**语言模式：** [LP30](../engineering/PATTERNS.md#lp30)、[LP27](../engineering/PATTERNS.md#lp27)。

**核心句：** “协商修订承诺，明确新旧义务何时交替。”

**展开：** “因〔变化〕，我提议将〔旧承诺及版本〕改为〔新条件〕。各受影响方是否按规则认可？请明确新旧义务何时交替、剩余义务是什么。”

**完成检查：** 新旧版本、认可、剩余义务与生效点明确。

**边界与失效：** 提议未接受前旧义务状态按原规则保留。

**可复用组成：** [A-P4](../models/M4.md#a-p4)、[A-P6](../models/M4.md#a-p6)、[A-P13](../models/M4.md#a-p13)、[A-P15](../models/M4.md#a-p15)、[A-P16](../models/M4.md#a-p16)、[I-C3](../models/M3.md#i-c3)。

**机制候选：** [ME10](../MECHANISMS.md#me10)、[ME12](../MECHANISMS.md#me12)。

## 协作（Coordination） {#coordination}

协作在本组指多个主体的任务、角色、依赖和交接怎样配合。依赖说明谁等什么，交接说明把什么转给谁；升级是将阻塞或争议交给有权角色或另一个处理流程。规则说明条件下的要求、允许或禁止；治理进一步说明规则由谁解释、执行、复核和修订。试走文档不能证明真实协作已稳定。

例如，规则写“缺来源不能通过验收”；出现争议时，还需知道谁解释“来源足够”、谁复核、谁能修订规则。这是从规则到治理所补的职责依据。试走则把“材料齐全”和“来源缺失”两个假想输入代入，检查是否找得到下一步及负责角色；它检查安排是否写得可处理，不等于现实中已经发生或反复可靠执行。

<a id="a-c8"></a>

### 依赖组织（Dependency Structuring） · A-C8

**状态变化：** 行动依赖不明 → 可追踪依赖结构。

明确输入、输出、前置条件、交接与阻塞。

**相邻区别：** 依赖组织说明谁等待什么及继续条件；[协调形成](../models/M4.md#a-c9)将依赖与任务、角色、责任和承诺组合为协调安排。

**操作入口：** [OP28](../engineering/OPERATORS.md#op28)、[OP29](../engineering/OPERATORS.md#op29)、[OP24](../engineering/OPERATORS.md#op24)。完整任务可参照[PR11](../engineering/PROTOCOLS.md#pr11)。

**怎样做：** 从一个具体执行步骤问它开始前必须取得什么，再沿这些输入追查提供者、版本和交接位置；逐步连出依赖，确认继续条件与阻塞处理。输入来源不明时保留缺口，不把等待关系当输入可用。

**语言模式：** [LP28](../engineering/PATTERNS.md#lp28)、[LP29](../engineering/PATTERNS.md#lp29)、[LP24](../engineering/PATTERNS.md#lp24)。

**核心句：** “从一步需要的输入，追查谁提供、怎样交接。”

**展开：** “〔具体步骤〕开始前需要什么输入？这些输入由谁提供、哪个版本、交到哪里？沿输入来源继续查，哪些步骤互相等待？请确认可继续条件，缺输入或交接失败时谁通知和处理，哪些来源还不明？”

**完成检查：** 每个关键步骤能指出等待对象和可继续条件。

等待对象明确不表示输入可用；选一个阻塞情境检查能否找到负责者和下一步。

**边界与失效：** 依赖描述不证明依赖输入已可用；循环依赖需处理。

**可复用组成：** [A-P9](../models/M4.md#a-p9)、[A-P14](../models/M4.md#a-p14)、[A-P15](../models/M4.md#a-p15)、[I-C3](../models/M3.md#i-c3)。

**机制候选：** [ME10](../MECHANISMS.md#me10)、[ME12](../MECHANISMS.md#me12)。

<a id="a-c9"></a>

### 协调形成（Coordination Formation） · A-C9

**状态变化：** 行动未协调 → 可运作协调结构。

组织角色、责任、任务、权限、依赖和交接。

**相邻区别：** 协调形成建立可运作的安排；[协调稳定](../models/M4.md#a-c10)根据反复使用的实际材料判断并改善其可重复性。

**操作入口：** [OP28](../engineering/OPERATORS.md#op28)、[OP29](../engineering/OPERATORS.md#op29)、[OP27](../engineering/OPERATORS.md#op27)。完整任务可参照[PR11](../engineering/PROTOCOLS.md#pr11)。

**怎样做：** 组织任务、角色、依赖与必要承诺；试走正常与阻塞情境；核对成立依据。

**语言模式：** [LP28](../engineering/PATTERNS.md#lp28)、[LP29](../engineering/PATTERNS.md#lp29)、[LP27](../engineering/PATTERNS.md#lp27)。

**核心句：** “接好任务与角色，试走正常和阻塞情境。”

**展开：** “请将〔各方任务〕的责任、权限、依赖、交接及必要承诺接成一份安排，并核对成立依据。正常情境如何推进，发生〔阻塞〕时下一步由谁处理？请相关方按规则确认。”

**完成检查：** 试走一个正常与一个阻塞情境能找到下一责任。

试走检查安排是否能指导处理；共同理解目标不自动建立行动安排。

**边界与失效：** 共同理解目标不等于行动安排已成立。

**可复用组成：** [A-C2](../models/M4.md#a-c2)、[A-C6](../models/M4.md#a-c6)、[A-C7](../models/M4.md#a-c7)、[A-C8](../models/M4.md#a-c8)、[A-P4](../models/M4.md#a-p4)。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-c11"></a>

### 规则形式化（Rule Formalization） · A-C11

**状态变化：** 规则含混／非正式 → 可适用的规则。

明确触发、要求／禁止／允许、角色、范围、例外与生效依据。

**相邻区别：** 规则形式化说明哪些条件下有什么要求或例外；[治理形成](../models/M4.md#a-c12)说明规则由谁解释、执行、复核和修订。

**操作入口：** [OP31](../engineering/OPERATORS.md#op31)。完整任务可参照[PR11](../engineering/PROTOCOLS.md#pr11)。

**怎样做：** 从一次或多次具体处理情境出发，先描述哪些行为需允许、要求或禁止及理由；比较情境差异，提出触发、范围和例外，再核对制定权限，用正常与边界例试判并确认生效。依据不足时保留规则提案。

**语言模式：** [LP31](../engineering/PATTERNS.md#lp31)。

**核心句：** “先比较具体处理情况，再试写规则。”

**展开：** “在〔具体处理情境〕中，哪些行为应允许、要求或禁止，理由和依据是什么？换一个情况，要求会改变吗？据此提出〔触发、范围与例外的规则草稿〕，核对来源和制定权限，用正常与边界例试判，再按安排确认生效。”

**完成检查：** 具体案例可判断适用、例外或需解释的地方。

**边界与失效：** 形式清晰不自动产生约束力，规则来源和权限需有效。

**可复用组成：** [A-P8](../models/M4.md#a-p8)、[A-P13](../models/M4.md#a-p13)、[A-P15](../models/M4.md#a-p15)、[A-P16](../models/M4.md#a-p16)。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-c12"></a>

### 治理形成（Governance Formation） · A-C12

**状态变化：** 规则存在但维护不明 → 治理与执行结构。

明确解释、执行、监测、争议处理、修改和复核角色。

**操作入口：** [OP31](../engineering/OPERATORS.md#op31)、[OP29](../engineering/OPERATORS.md#op29)。完整任务可参照[PR11](../engineering/PROTOCOLS.md#pr11)。

**怎样做：** 从一项规则及一个可能争议或违规报告试走：谁接收、解释、决定处理、复核以及修改；查各职责的现有来源，缺角色时提出安排并取得所需确认，再核对路径是否能处理情境。

**语言模式：** [LP31](../engineering/PATTERNS.md#lp31)、[LP29](../engineering/PATTERNS.md#lp29)。

**核心句：** “先试走一项规则争议，再补维护职责。”

**展开：** “对于〔规则〕，若发生〔争议或违规报告〕，谁接收、谁解释、谁决定处理、谁复核，依据分别在哪里？缺少职责时怎样提出安排并取得确认？谁能按有效程序修订规则？请试走这个情境，哪些地方仍找不到处理者或依据？”

**完成检查：** 可说明谁如何处理规则冲突和违规报告。

缺少角色或来源时明确记录，并用一个争议例检查是否找得到有效处理路径。

**边界与失效：** 有治理结构不等于执行有效；结果需另测。

**可复用组成：** [A-C4](../models/M4.md#a-c4)、[A-C7](../models/M4.md#a-c7)、[A-C8](../models/M4.md#a-c8)、[A-C11](../models/M4.md#a-c11)。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-c10"></a>

### 协调稳定（Coordination Stabilization） · A-C10

**状态变化：** 临时安排 → 可重复协调方式。

基于实际使用修订交接、替补、升级与检查节奏。

**操作入口：** [OP31](../engineering/OPERATORS.md#op31)、[OP30](../engineering/OPERATORS.md#op30)、[OP37](../engineering/OPERATORS.md#op37)。完整任务可参照[PR11](../engineering/PROTOCOLS.md#pr11)、[PR12](../engineering/PROTOCOLS.md#pr12)。

**怎样做：** 取得反复使用的实际材料；检查正常、异常与交接；据反馈修订并再次观察。

**语言模式：** [LP31](../engineering/PATTERNS.md#lp31)、[LP30](../engineering/PATTERNS.md#lp30)、[LP39](../engineering/PATTERNS.md#lp39)。

**核心句：** “依据反复执行的材料修正协调安排。”

**展开：** “〔协调安排〕在重复使用中，实际交接、阻塞与异常分别怎样发生，记录是什么？哪些环节可靠，哪些需要按有效程序修订？修订后继续取得哪些使用材料来检查？”

**完成检查：** 正常、异常与交接情境可重复执行，问题有反馈。

依据反复执行材料判断可重复性；一次试走或一份流程文档不足以证明稳定。

**边界与失效：** 一份流程文档不足以证明稳定，需 O-C3 的使用反馈。

**可复用组成：** [A-C9](../models/M4.md#a-c9)、[A-C11](../models/M4.md#a-c11)、[A-C12](../models/M4.md#a-c12)。

**跨域过程引用：** [O-C3](../OUTCOMES.md#o-c3)。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

<a id="a-c13"></a>

### 行动关系修订（Action-Relation Revision） · A-C13

**状态变化：** 有效安排出现异常／变更 → 有依据的更新状态。

处理任务阻塞、取消、失败报告、权限撤销和责任重分配，按权限与影响确认更新。

**操作入口：** [OP30](../engineering/OPERATORS.md#op30)、[OP29](../engineering/OPERATORS.md#op29)。完整任务可参照[PR12](../engineering/PROTOCOLS.md#pr12)。

**怎样做：** 定位异常与受影响关系；按权限提出或确认变更；记录剩余义务和下一责任。

**语言模式：** [LP30](../engineering/PATTERNS.md#lp30)、[LP29](../engineering/PATTERNS.md#lp29)。

**核心句：** “根据新情况更新安排，保留未结束的义务。”

**展开：** “因〔新情况〕，〔原安排及版本〕中的哪些任务、角色、权限、依赖或承诺受影响？请提出修订，按规则确认，并说明新版本、生效点、剩余义务及下一责任。”

**完成检查：** 记录事件、依据、受影响关系、剩余义务及下一责任。

报告异常不自动修改有效安排；未生效部分与已生效修订分开记录。

**边界与失效：** 新增复合接口；逾期不自动解除承诺，任务取消不自动撤销全部相关义务。

**可复用组成：** [A-C1](../models/M4.md#a-c1)、[A-C3](../models/M4.md#a-c3)、[A-C4](../models/M4.md#a-c4)、[A-C9](../models/M4.md#a-c9)、[A-C12](../models/M4.md#a-c12)、[A-P6](../models/M4.md#a-p6)。

**机制候选：** [ME12](../MECHANISMS.md#me12)。

| 对象 | 主要状态 | 更新／关闭依据 |
| --- | --- | --- |
| Request | 提出、待响应、接受、拒绝、协商、延后、撤回 | 响应或有权请求方撤回；协商与延后可仍开放 |
| Task | 已定义、已指派、已接受、进行中、阻塞、已提交、已验收、取消、失败 | 任务版本、执行证据、验收或按权限处理的异常 |
| Commitment | 有效、到期未履行、履行、解除、被修订 | 到期只是事件标记，不自动判定原因或解除义务 |
| Authority | 主张、确认、有效、委托／转移、失效／撤销 | 权限来源、范围、期限和生效事件；技术访问另核验 |
| Responsibility | 主张、确认、持续、重分配、结束 | 有权角色的认可和责任范围，不据任务关闭自动结束全部角色职责 |

这些是生命周期词汇，不是为了每个词再制造一个 Primitive。A-C13 组织异常更新。没有证据时，记录“状态未知”而不是擅自跳到完成。

**共同规格字段**：任务 ID／版本、目的、范围、交付、约束、执行者、负责者、依赖、验收规则与角色、期限或检查节奏、阻塞及变更处理。按任务省略不必要字段，但关键空缺不得伪装为已确定。

## 任务就绪的四项检查

规格完整、安排成立、执行条件可用、结果满足分别记录。A-C6 说明规格足以指导执行与验收；是否有人按有效安排承担，以及此刻资源／权限／输入是否可用，另查对应关系和现实材料。

一项可明确描述的任务可以仍然等待接受或关键输入。检查发现不能开始时，记清缺口，不因为规格文字齐全就声明运行就绪。后续角色认可也不回溯为之前已经接受。

A-P9 的任务对象进入指定沟通或工作安排时按其规则登记；个人草稿里的“准备做某事”首先是内部任务／计划表征，不能仅凭文字中出现任务名认定已建立他人义务。

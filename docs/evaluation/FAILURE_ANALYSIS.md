# 失效分析：先定位，再修订

同样的“没做好”可以来自不同缺口。下表是诊断工作表，不声称所有失败可唯一归类；信息不足时保留多个候选。先依据材料定位，不凭解释流畅程度确认原因。

| 观察到的问题 | 需要检查 | 合适处理 | 不合适的反复操作 |
| --- | --- | --- | --- |
| 输出详细但没有解决原问题 | 工程任务、主体目的和范围是否正确 | 重审任务或缩小范围 | 继续添加章节和术语 |
| 只会重复例句 | 是否识别了原问题的缺口 | 用边界和新例检查理解，减少必要术语 | 增加更多固定问句 |
| 起手问题就答不上来 | 是否要求先具备接口要形成的名称、标准或路径；还是缺必要材料？ | 从现有线索、具体描述或实例进入；事实、领域方法或权限缺失时先取得输入 | 把同一结果要求换词再问，或强填答案 |
| 标准已定，却仍无法判断 | 缺判断规则，还是缺输入材料？ | 有规则时取所需材料；没有规则时补规则 | 无限制重做目标澄清 |
| 候选很多但都同义 | 候选是否在任务相关条件上不同 | 换前提、手段或关系生成实质不同项 | 单纯要求再来十个 |
| 判断表完全由 AI 生成 | 谁掌握、谁判断，检查材料是什么？ | 分开文本质量与主体表现，取独立新例材料 | 用产物长度证明能力提升 |
| 双方明白却反对 | 是否是价值、标准或选择分歧 | 结构化分歧，确认处理方式 | 强迫复述直到同意 |
| 接受任务但无法开始 | 资源、权限、输入和技术条件是否具备 | 修复条件、重安排或报告阻塞 | 只重复催促与承诺 |
| 文件提交后仍被退回 | 是否满足当前标准；版本和验收依据是否相同？ | 定位不满足项，或按授权澄清规则变化 | 把提交记录当完成证明 |
| 协议说完，目标还未实现 | 是未执行、无产物、部分达成还是未知？ | 按使用规格分别记录，选择继续或停止 | 一律标“成功完成协议” |
| 操作后变化，原因不明 | 有无前状态、比较材料和竞争解释？ | 缩小为可支持主张，必要时设计验证 | 直接归因于 CLE |
| 流程运行成本超过收益 | 当前检查是否需要每一步？ | 复用已有状态，删减或改用单算子 | 为体系完整要求全流程 |
| 重复练习后仍无法独立使用 | 是否缺领域材料、基础知识或反馈？ | 针对缺口训练，或补实际经验 | 默认只因态度或努力不足 |

## 一份具体的失效记录

1. **期待**：本次要达到哪种状态或输出？
2. **观察**：实际出现什么，有什么材料？
3. **差距**：哪些满足、哪些不满足、哪些未知？
4. **候选原因**：任务、输入、操作、模式、顺序、环境、关系或标准的哪些部分可能有关？
5. **区分检查**：什么下一份材料能区分至少两种候选？
6. **处理**：查证、修订、换操作、实际执行、协商或停止；社会修订按适用规则生效。

例：段落增加了许多术语。若已约定“关键术语须附解释”，且检查发现没有解释，可判该文本条件未满足并修订；若规则只有“清楚”且双方含义不同，先查标准与共享。若要判断初读者是否理解，仍需其表现材料；没有材料时，不能仅凭术语多少判理解成功或失败。

## 修改整个体系的条件

若失效来自特定输入或语言变体，先修调用与例子；若多个场景反复暴露同一状态接口混合不同输出，才重审粒度；若来源不支持某结论，修证据主张而非新增机制名称。保持 ID 可追溯，重要变化写入决策和版本记录。

失效可以说明局部方案不适用，不自动证明整个体系无效。反过来，解释出一条失败原因也不证明体系有效；仍需实际处理及其检查材料。

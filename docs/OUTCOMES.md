# Outcome Registry｜结果与反馈

结果（Outcome）指实际行动后观察到的情况，核验是按适用规则检查它满足什么，反馈是将这些材料带回原判断或安排。区分安排、执行尝试、观察结果和条件判定。不存在“说清楚任务，所以现实已经改变”的自动箭头。

例如，文件上传记录可支持文件已到达；内容是否准确须取得文件并按指定原材料核验；若缺来源，可提出补来源的修订建议；只有实际补齐并更新后，才记录该修订完成。每句话都使用上一项真实取得的材料，而不是由“上传成功”跳到“内容准确”或“已经修好”。

<a id="o-c1"></a>
## O-C1. Execution-to-Observation

行动尝试 → 带来源、时间和环境的观察结果。行动可以由个人、团队或技术系统实施，可能成功、失败、部分完成或未执行。记录操作、环境、输入、输出及外部影响；不将工具返回的“成功”自动当成最终业务结果。

<a id="o-c2"></a>
## O-C2. Outcome Verification

观察结果＋适用标准 → 满足、未满足或无法核验。用约定材料与方法核验，区分事实条件是否满足与谁有权关闭社会任务。连接 M2 评价、M3 确认和 M4 A-P5/A-P11；缺失材料进入未知，不填为通过。

<a id="o-c3"></a>
## O-C3. Feedback Integration

已评价结果 → 对目的、语言、标准、模型、计划或安排的修订建议与有效更新。区分“需要修改”的发现与修订实际生效。通过 B-C8 回到四模型。

## 结果不等于效果归因

完成一次交付只证明该次结果；要说明协议使结果改善，需要对照、重复或能排除替代解释的材料。系统日志、输出与主体反馈各有盲区。

最小记录：做了什么、观察到什么、依据什么标准、结果状态、未知／异常、下一步。原则上不强制所有应用计算总分。

## 反馈可以保持原安排

O-C3 的有效输出可以是保留当前判断／安排并注明依据，也可以是修订提议或已生效更新。收到反馈不要求必然改动；同样，只发现需改动也不表示已经更新。分别记录结果核验、修订决定与生效状态。

外部材料不足时，写清要获取什么及其用途；没有前状态时不从当前产物倒推变化。取得新材料、实施试验或真正修改环境属于现实操作，不能用更详细的语言记录代替。

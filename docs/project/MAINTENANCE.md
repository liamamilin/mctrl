# 维护约定

## 单一正文与版本

docs 是正文权威来源。模型、算子、协议、案例和证据在同一个项目中维护；在线电子书由这些文件构建。聊天可提供新材料，但缺失上下文不能靠猜测补写。

Core v0.7 表示当前完整规范版本；project-v0.7.8 表示包含正文、来源、配置和检查记录的交付快照。小范围修辞修订可改快照补丁号；模型边界、状态接口或协议行为改变应说明规范变化，必要时升规范版本。不要求每个文件独立增版本。完整规范沿用v0.7；project-v0.7.5记录新增复合接口R-C2，project-v0.7.6打磨该新接口的解释与完成依据，project-v0.7.7统一M1所指组命名，project-v0.7.8逐项审查接口入口与结果前置；原81接口定义与旧冻结版本保留，新增依据见[决策009](../decisions/009-identification-entry.md)。

v0.5 已由用户初步冻结。project-v0.5.2 将原v0.1操作手册重构为结构核心子体系v0.2；project-v0.5.3 按用户要求冻结此版本，保留原层次与ID，不改写冻结组件定义。权威正文为 `docs/essentials/index.md`，逐项选择依据为 `docs/essentials/SELECTION.md`；页面模板与CSS只负责呈现。冻结正文与审计副本位于archive/structural-core-v0.2-frozen，manifest.json记录SHA256；后续打磨使用新版本，不覆盖此快照。核心、支撑和扩展分别记录，复合组成和特化父接口必须闭合；条件机制与跨域引用不能机械当执行依赖。母体系与子体系同一次构建、同一Pages发布，跨入口用相对链接；调整路径时同时检查两个方向。

## 修订过程

1. 记录具体任务、反馈、失败或新证据，并定位相关 ID。
2. 检查现有接口能否表达问题；优先修订边界、变体和调用方式。
3. 明确修改是否影响定义、机制解释、工程行为或证据范围。
4. 在已授权工作范围内直接完成相应修改；只有目标或授权范围实质不明时再澄清。冻结内容可以经授权修订，冻结不意味着不可变。
5. 同步修改依赖页、实例、来源和索引；重要决策写入 decisions，更新 CHANGELOG 与 STATUS。
6. 更新派生 Registry 快照；执行链接、ID、依赖检查和严格构建。

## ID 与证据

ID 不重新分配给无关含义；撤销时保留历史和替代关系。Specialization 保留旧编号，但不重复宣称独立机制。新增 Primitive 须写明现有接口为什么不足；其粒度是工程约定。

工程定义被采用与实证支持分开。新增引用先检查实际支持范围，不根据论文标题补写结果；全文未读则明确标记。研究没有支持时保留 E0，不能通过增加术语提升证据等级。

## 检查与发布

运行README列出的登记表、主线、正文和核心检查，再执行严格构建。正式发布前完成用户已授权的具体发布范围与所需配置；没有实际部署输出时不填写虚构在线链接。PR 只检查，main 的发布按工作流配置执行。

构建后运行 `python scripts/check_site.py` 检查生成页面的链接、锚点和本地资源；该检查也在 Pages 工作流中运行，覆盖子体系模板新增的导航链接。

修订核心选择后运行 `python scripts/check_essentials.py`，核对候选全集覆盖、模型组成／特化闭包、主讲模式对应及完整协议的算子引用。该检查不证明预计频率或收益判断正确；调整筛选依据需依赖实际使用材料。

不按固定时间自动修订；新问题、新材料或用户修改要求是触发。没有实际执行的试验，不在版本记录写“效果已验证”。

派生快照在正文修改后执行 `python scripts/update_registry.py`；检查执行 `python scripts/update_registry.py --check` 和 `python scripts/check_docs.py`。文档需要先定义关系类型，再由脚本检查引用，不通过脚本把描述关联误判为执行依赖。

结束记录与目标检查同步修订。新的真实失败进入失效分析和边界例，学习效果需要独立记录。已有状态仍有效时复用，版本或环境变化时重新核对关键前提。

## 概念解释的维护

关键术语须说明指什么、例子及与相邻概念的边界；首次进入主线或有关模型时就近解释，集中定义在术语表回查。只出现英文、用途或状态箭头时重新审查；同词不同用法须标明对象或层级。动作型接口已经有明确输入、动作、输出时，不为覆盖而再造抽象名词。定义澄清与新效果主张分开。

句子审查还须核对所指对象与范围、依赖的前文知识、从上一概念到本句的依据，以及结论所需材料。缺连接时补一个必要条件、推理或连续例子；无法补依据时收窄说法或保留未知。例子的设定、假想输出、现实观察分开；不能以“举了例子”代替论证，也不能用一条总免责声明掩盖局部跳步。普通词和已足够清楚的句子不机械扩写。这是作者维护方法，不增加读者必学层级。

## 当前完整体系维护

完整v0.7承接v0.6修订，原v0.5与结构核心v0.2冻结内容保留，v0.6末次工作稿另存快照。接口卡为学习连接的权威正文；改方法时同步算子、模式、完整索引、相关案例与训练。P7约束新增模型接口与方法，不以目录覆盖为理由机械新增组件。

每轮执行check_mainline.py、check_docs.py、update_registry.py --check、严格构建及check_site.py。结构核心v0.2的原全集审计使用archive/full-v0.5-frozen的算子与协议，避免将完整体系后续新增内容硬塞入旧冻结选择。

原则正文须先解释主张所指，再说明例子中从条件到判断的联系及适用边界，最后提供回查表。仅给名称、约束和错误，不能当作初学者已经获得解释。

语言模式统一用一条核心句与展开表示。核心句提示一个操作方向、供直接背诵；展开提供可以用于自问、表达或交流的语言形式，说明对象、处理与所求响应；作者侧判断说明放到完成检查或边界。逐项对照状态变化及算子，不以“带槽位”或“提到接口名称”作为功能吻合的依据；也不要求单个模式独自完成整个复合接口。具体情境例句与实际语言实例分别标明。修订同步模型、算子、模式库、导读、训练与检查，保留稳定ID。


## 正文与语言模式的写作约定

以下是本项目采用的写作约定，不是新的正式原则或模型层，也不表示符合任何外部语言标准。

- 同一概念使用固定名称；首次需要时就近解释，术语表供回查。
- 一个句子优先说明一项主要动作或判断；条件影响理解时先说明条件，步骤较多时分句。
- 让对象和指代可追溯；当前判断依赖的条件不省略，已有前文不重复填充。
- 区分材料、推断、候选和设想；没有材料时保留未知。
- 核心句帮助记住方法，展开提供能直接使用的表达；不要把整段维护说明塞进说给对方的话。
- 完成检查说明可观察的表现、产物或成立依据；具体检查按目标选择，不为整齐要求每次记录全部字段。

补充检查解释放在既有完成检查下，原定义字段与稳定ID继续保留。模型、算子与组合模式中的局部表达可以不同，但具体动作与目标不能漂移；任务处理或其他变体须保留相应前提。

## 结果前置的审查

“结果前置”指把接口要形成的结果或能力，当成读者已经具备的起手条件。例如，指认尚未确定对象名称，却让读者先指出对象并命名；标准尚未形成，却让读者直接给出规则。

逐项检查读者已有输入、第一步可做什么、这一步怎样帮助形成候选，以及后续怎样检查。核心句可以提示方向，但展开或方法必须有入口。先从线索、原话、具体情境或材料开始，再描述、对照、询问或提出草稿；候选位置可以在处理中逐轮填入，不能要求初始已有答案。

已有目标、待审查假设、真实交付、领域方法和有效授权等可能是合法输入。缺失时说明怎样取得、返回哪个已有接口或保留未知，不靠问法替代材料。“请你……”或“我承诺……”等表达本身可能是语言行动，不能仅因它要求一个结果就判为此缺口；仍需检查适用条件与实际成立依据。

本规则用于作者维护，不新增读者必学层级，不声称文字入口能保证任何读者学会。审查记录见scripts/entry-audit-review.json，决策见[010](../decisions/010-entry-audit.md)。

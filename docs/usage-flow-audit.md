# mctrl V1 使用动线分析

日期：2026-10-09。依据当前工作区实现、393 × 852 手机尺寸下的隔离浏览器走查，以及用户补充的实际工作方式。先按真实工作场景分析，再列页面跳转证据。下文记录打磨前的基线；本轮实现见文末，正在运行的任务保持连续。

## 真实工作动线

产品需要围绕三条工作主线设计。启动位置与使用目的分别影响路径；“只看近况”和“回到电脑”是这些主线中可反复发生的阶段。

### 1. 手机发起交互式工作

用户给出的实际路径：打开手机 App → 创建 Shell → cd 到目录 → 打开 harness（如 Codex/OpenCode）→ 交互 → 暂时离开 → 再次继续。

当前实现还要求先选择已注册 Project；Shell 在该 Project 的目录启动。目标项目已注册且选对时，可以省去 cd。临时目录没有注册、只知道部分路径、目录名需要从输出复制时，用户仍要在手机上完成查找、抄写、输入和校验。

路径中最明显的摩擦：

- **到达目标目录。** 目录是启动工作的前提，用户需要同时理解 Project 注册、Shell 的初始目录与 cd 后的当前目录。已经知道路径的用户也要跨页注册。
- **把输出用于下一步输入。** 用户反馈手机上不能直接复制终端输出。当前没有产品层的复制选区、复制输出或“复制当前路径”控件；xterm 自身的选择机制不能代替已验证的手机复制动线。详情中的纯文本预览可以作为候选复制载体，但目前要退出终端再进入，也没有专门复制入口。
- **启动 harness 后的长文本交互。** 直接终端输入、中文输入法、回车、翻页和输入框之间的切换共同决定体验。当前结构化输入是否受支持由创建时的 Runner 身份决定，Shell 内手动打开 harness 与直接选择 Codex/OpenCode 存在不同的支持结果。
- **观察谁还在运行。** 该路径记录的是 Shell Managed Work，Shell 仍活着时 RUNNING 不能证明手动启动的 harness 仍在运行。应展示已知的会话/进程事实与输出，不推断 agent 的含义。

这条路径的现有快捷分支是：选择已注册项目 → 直接选择 Codex/OpenCode → Prompt 留空 → 打开终端交互。它复用已有启动能力，可以减少手动 cd 和键入 harness 命令；仍需保留 Shell 路径的自由度。

优先打磨：让常用项目与初始目录更易选择，明确显示当前路径；提供手机可用的输出/路径复制以及可检查的粘贴方式；使 harness 交互的文字输入与快捷键容易到达。文本复制/粘贴不会自动执行 cd 或命令，发送动作需要保持现有的明确触发与不重放规则。

### 2. 电脑发起，手机接续同一交互

真实路径：电脑在项目目录打开终端 → 启动 harness 并交互 → 离开电脑 → 打开手机 App → 识别原会话 → 继续输入 → 回到电脑继续。

当前必要条件：原程序运行在 mctrl 所连接的 tmux 服务内。已有外部 tmux 会话可以直接发现，不需要额外注册 Project。普通 Terminal/iTerm 窗口里的非 tmux 进程当前不能自动出现在手机上，也不能把一个已经运行的普通终端进程无缝搬入 tmux。通过 harness 自己的恢复命令重开对话属于另一条恢复路径，不等同于接续原进程。

主要摩擦发生在电脑端的前置准备与手机端的识别：

- 用户在电脑开始工作时，需要知道怎样让这次工作之后可从手机接续；当前 Pair.app 只处理设备配对。
- 手机上需要从名称、目录和输出快速认出原会话；外部 tmux 会话没有 Managed Work 状态标签。
- 接入后还要看得清 TUI、翻得到历史并输入文字；当前只接入 Session 的活动窗口/窗格，其他窗口/窗格是只读清单。
- 回到电脑时应继续附着同一 Session。关闭手机页面只断开手机连接，Close Session 会终止工作，两者必须容易区分。

优先打磨：电脑开始工作时的可接续入口/说明；手机上的最近会话、清晰身份与上下文预览；同一会话的持续性反馈。不要让用户在离开电脑后才发现原终端不在可接续范围内。

### 3. 手机下达任务，稍后查看结果

真实路径：手机打开 App → 选择已注册项目与 Codex/OpenCode → 填写任务 → 启动 → 关掉手机 → 稍后看输出和退出事实 → 必要时再开下一次工作。

这条主线使用当前非空 Prompt 的非交互启动方式。用户的首要需求是提交、确认已启动、回来认出那次执行与阅读输出；不要求先创建 Shell 并手动启动 harness。进程退出码与输出是可展示事实，不能直接宣称业务任务成功。

主要摩擦：页面没有充分说明这种启动与交互式启动的差别；返回时找任务仍依赖 Session；非交互 JSON 输出可能较难阅读；Session 被关闭后普通 Work 历史没有独立浏览入口。当前真实模型调用仍有账户/提供方配置验收缺口。

优先打磨：启动方式预告、提交后明确的执行身份、之后可找回的记录与容易阅读的输出。继续遵守 V1 对 agent 语义状态的限制。

### 横跨三条主线的短路径

- **只观察、偶尔介入：** 打开 → 找到会话 → 看输出 → 必要时进入终端做一个操作 → 离开。它不需要经过创建流程，应当是已有会话最短的使用路径。
- **手机工作转回电脑：** 找到并附着同一 tmux Session。属于交互主线的后半程。
- **断线后回来：** 恢复连接并核对输出，不重放不确定的输入。属于所有主线的异常分支。

### 按真实工作路径调整优先级

1. 手机输入基础：输出/路径复制、可检查的粘贴、目录上下文、长文本与回车。
2. 电脑与手机接续：启动前知道会话是否可接续，切换后快速找对原会话。
3. 手机启动捷径：已有项目直接打开 harness，明确交互式与一次任务的区别。
4. 再优化页面信息层级、设置分组与恢复入口。

## 产品要服务的使用场景

用户离开 Mac 后，在手机上确认已有工作是否仍在运行、查看输出、必要时介入，也可以启动新的工作；回到 Mac 后继续同一个 tmux 会话。日常闭环是：打开 → 找到工作 → 看近况 → 必要时操作 → 离开 → 再次回来。

当前主导航是 Home、Start、Settings。Session Detail 属于 Home 分支，Terminal 是独立全屏页面，退出后回到 Session Detail。

## 动线中的主要摩擦

1. **首次启动会中断上下文。** 项目注册入口跳到设置顶部，用户需要寻找项目区，注册后再自行返回启动页并选中项目。项目名称、Mac 路径、默认 Runner 三个新概念也同时出现。
2. **可选 Prompt 隐藏了重要的启动差异。** Codex/OpenCode 留空时打开交互界面；填写时执行一次非交互任务。Shell 的文本则发送至 Shell。页面统一称为 Prompt，留空提示还写着“在 Mac 上输入”，弱化了手机操作的用途。
3. **观察路径的信息顺序有偏差。** 详情先呈现会话元数据、终端入口、关闭入口、多个进程字段，最近输出排在后面。只想看近况的用户要先越过维护信息；高频操作与终止操作又相邻。
4. **终端存在点了才知道不能用的控件。** 结构化 Prompt 框对 Codex/OpenCode 仍显示且能点击 Send，随后后端拒绝。输入方式应依据已知 Runner/会话事实提前说明或收起。
5. **再次回来时，识别成本偏高。** 会话卡片与详情主要使用带随机后缀的 tmux 名称；Project 名称、Runner、开始时间可以更直接地帮助识别工作。当前没有最近访问或继续上次的入口。
6. **恢复入口较深，设置承担过多职责。** Transport、终端尺寸、Projects、Work 恢复、设备与 API 边界都在同一长页。失联工作在首页消失后，用户需要知道去设置寻找。
7. **已安装与可实际使用混在一起。** Runner 检测主要确认可执行文件和版本，前端显示 Ready to launch；当前已知 Codex 模型/账户与 OpenCode 订阅问题说明这一文字无法表达真实可用范围。

## 建议的打磨顺序

### 第一轮：让关键路径连续、可预期

- 注册项目入口定位到项目区，保留来源；成功后提供“使用此项目启动”，带项目 ID 返回表单。
- 根据所选 Runner 与 Prompt 内容显示启动结果预告。例如“打开 Codex，进入终端后输入”或“提交这段任务，执行结束后保留输出”。不引入新的执行状态或推断 AI 语义。
- 结构化输入框只在已知支持的会话中可发送；其他会话提供直接终端输入的明确入口。保持不重放未知输入的协议规则。
- 详情顶部依次呈现项目/Runner、进程事实摘要、最近输出与终端入口；PID、启动阶段等进入展开的技术详情，终止入口放在页面后部。

### 第二轮：让回来继续工作更轻松

- 首页以项目名和 Runner 帮助识别 Managed Work，保留真实 Session 名称作为次级信息；外部 tmux 会话继续保留原名。
- 增加最近访问的会话入口，失效时解释会话已不可用并返回列表。
- 首页展示需要检查的 Work 数量与恢复入口；恢复操作仍执行现有后台校验。
- 设置提供清晰的分组入口，将终端尺寸、版本与 API 边界等较少使用的信息折叠。
- 按当前浏览器上下文提供配对/PWA 使用指引，解释另一浏览器为何需要链接。

## 后续验收指标

- 尚无项目时，用户能沿同一条路径注册、选中并启动第一个项目。
- 看近况时，详情首屏可见进程状态和最近输出，不要求先读 PID/阶段。
- 启动前能理解所选 Runner 留空和填写文本分别会发生什么。
- 界面不提供已知会被后端拒绝的结构化输入操作。
- 返回产品时，能认出并继续上次会话；失联记录有可发现的解释和入口。
- 离开、终止、注销项目、撤销设备的结果始终清楚；既有持久性与输入不重放测试继续通过。

## 本轮已实现的动线打磨

- 手机从已注册 Project 直接进入指定目录；记住最近成功选择。无项目时注册入口定位到项目区，注册后携带新项目返回启动表单。
- Codex/OpenCode 默认“Open & interact”；“Run a task”要求任务文本。启动前显示结果预告，Runner 安装检测不再宣称账户可用。
- 终端顶部 Copy 打开原生文本选择面板，支持复制输出/路径、选区加入草稿、Shell 下准备已引用的 cd 命令。所有 Runner 都有正常文本草稿，Insert 保留原文且不带回车，⏎另行触发。
- 多行草稿检查客户端和活动程序两层粘贴模式，并在插入前刷新程序事实。启动未完成时不接收、不排队输入；切换 Session 使用独立终端状态。
- Shell cd 后展示经过 Runner/Attempt 和父子进程验证的当前子进程目录；不能验证时明确显示 Starting path。
- 首页加入继续上次会话、待检查 Work 入口、电脑先在同一 tmux 中启动的说明；最近会话按 id/name/Work id 校验，防止 id 复用误接。
- 详情先显示项目、状态、目录、终端入口与输出，技术字段和终止操作折叠。保留进程状态与任务业务结果之间的区别。

自动化覆盖与本机视觉走查结果记录在 `VALIDATION.md`。实体 iPhone 的选择手柄、系统 Copy 菜单及键盘切换仍需要设备上验收。完整任务历史浏览、文件浏览器、普通终端进程搬迁及模型账户配置不属于本轮实现。

## 第二轮：缩短启动与回来继续的路径

- 手机交互现在是：选择项目/Runner → Start Work → 直接进入终端。一次任务则直接进入输出页。只有已接受、尚无 Session 时，页面只查询同一个 Work，最多跟进 30 秒，然后提供手动查询；连续点击不会重复创建。启动失败显示原因和返回设置入口，离开页面后不会因迟到的 Session 查询结果自动跳转。
- 从输出取回文字会替换草稿选区或插入光标处，保留前后文字并把焦点交还草稿；不会立即发送。路径输入区域使用面板全宽，复制操作的点击高度至少 44px。
- 输出预览去除末尾空窗格行，打开时定位最新内容。查看旧输出或选择文字时，刷新保留当前快照；用户点击“Show latest output”后再切换。复制面板显示捕获时间。
- 回到前台立即刷新会话/进程事实，首页卡片能显示最新非空输出，终端优先显示项目名；刷新只读取状态，不发送命令、不重放输入。

这轮继续沿用已有 Project、Work、Session、tmux 与 Runner 边界。实体手机的系统选区、键盘弹出和输入法体验仍单独验收。

## 第三轮：电脑发起 → 手机接续 → 回到电脑

- 安装短命令后，WezTerm 中进入项目目录 → `mctrl here` → 照常启动 harness。连接地址和目录对应的会话名由程序处理，手机自动发现这个外部会话。此入口不要求注册 Project，也不创建 Managed Work。
- 同一物理目录重复执行时接回原会话，保留进程与当前工作现场；同名但路径不同的目录使用不同会话。守护进程把有效连接写入私有的 `desktop.json`，终端无需继承 launchd 的环境变量。
